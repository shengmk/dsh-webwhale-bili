# 工作流搭建学习笔记

> 目的：把“能演示的自动化”变成“能长期运行、不会乱发消息、可回放、可人工接管”的工作流。
> 结合 `dsh-webwhale-bili` 这次真实翻车（重复消息、兜底刷屏、分不清自己和对方）整理。

---

## 1. 先分清三个东西

| 概念 | 本质 | 适合 |
|---|---|---|
| Prompt / 单次调用 | 一次输入一次输出 | 简单问答 |
| Agent | 模型自己决定下一步 | 探索、开放任务 |
| Workflow | 预先定义的节点和边 | 可重复、要审计、要控成本 |

结论：

```text
能用 workflow 固定的，不要交给 agent 即兴决定。
LLM 适合放在“理解”和“表达”节点，不适合放在“是否发送”这种边界节点。
```

Rasa 的 CALM 也是这个思路：LLM 做对话理解，业务逻辑用可预测的 flow。

---

## 2. 一个可靠工作流的最小骨架

```text
Trigger
  ↓
Guard（幂等 / 权限 / 频率）
  ↓
Context（会话 / 记忆 / 人格）
  ↓
Router（意图分类）
  ↓
Action（回答 / 查询 / 工具 / 人工）
  ↓
Validate（相关性 / 安全 / 格式 / 长度）
  ↓
Outbox（待发送）
  ↓
Send
  ↓
Record（审计 / 记忆 / 指标）
```

### 每个节点只做一件事

- Trigger：只负责产生事件
- Guard：只负责拒绝，不负责生成
- Context：只负责取数据，不生成
- Router：只输出意图和置信度
- Action：只执行动作
- Validate：只校验，不修内容
- Outbox：只排队，不直接发
- Send：只有一个出口
- Record：只追加，不改历史

## 3. 状态机比“大 if/else”可靠

每个会话一个状态：

```text
WAITING
  ↓ 收到新消息
RECEIVED
  ↓ 幂等检查
CLASSIFYING
  ↓
ANSWERING / ASKING / QUEUING / IGNORING
  ↓
VALIDATING
  ↓
SENDING
  ↓
WAITING
```

失败状态：

```text
RETRYABLE_ERROR
PERMANENT_ERROR
UNKNOWN_OUTCOME
NEEDS_HUMAN
```

原则：

- `UNKNOWN_OUTCOME` 不自动重试
- `NEEDS_HUMAN` 不进发送队列
- 同一会话同一时间只允许一个 run
- 对方没有新消息，状态保持 `WAITING`

---

## 4. 幂等：不要用“时间”当唯一判据

### 错误做法

```text
每 90 秒扫一次
→ 看到消息就回
→ 内存里记 seen
→ 重启后 seen 清空
→ 又回一次
```

### 正确做法

每条入站消息都有稳定键：

```text
idempotency_key = account_id + talker_id + msg_id
```

处理前：

```text
如果 key 已处理 → 直接退出
如果 key 正在处理 → 退出（并发锁）
如果 key 未处理 → 创建 run
```

发送前：

```text
outbox_key = run_id + reply_hash
```

同一个 run 只能产生一条出站消息。

---

## 5. Outbox 模式：发送和业务分开

不要：

```text
生成回复 → 直接调 B站 API
```

要：

```text
生成回复
→ 写入 outbox（pending）
→ 限速器批准
→ sender worker 发送
→ 标记 sent / failed / unknown
```

好处：

- 可审计
- 可人工取消
- 可重试
- 可限制频率
- 不会因为 UI 刷新重复发

---

## 6. 频率控制要分层

至少四层：

1. 单条消息去重：同一 `msg_id` 只能回一次
2. 单轮限制：对方再次回复前最多 1 条
3. 会话冷却：20 分钟
4. 每日上限：3 条/会话

再加：

- 全局发送预算
- 夜间静默
- 失败退避
- 熔断

这次翻车就是只有“内存 seen + 10 分钟 lastSent”，没有持久化幂等键和 outbox，旧定时器一多就重复。

---

## 7. 并发与单例

同一个账号只能有一个轮询器。

```text
start()
  → 如果已有 active，先 stop()
  → 创建新的 active
  → active 全局唯一
```

停止时要：

- 清定时器
- 设置 stopped
- 正在执行的 tick 检查 stopped
- 清 active
- 不再发起新请求

否则：

```text
重载一次 → 多一个定时器
再重载 → 再多一个
→ 同一句话发多遍
```

## 8. 身份与方向

消息必须有：

```text
account_id   当前账号
talker_id    对方
sender_id    这条消息的发送者
direction    inbound / outbound
msg_id
at
```

判断：

```text
sender_id === account_id → 自己发的
sender_id === talker_id  → 对方发的
```

不要把“会话对象”当成“发送者”。

UI、记忆、路由都要用同一套方向判断。

---

## 9. 人格、记忆、事实分开

### 人格层

只负责：

- 称呼
- 语气
- 口癖
- 句长
- 颜文字密度

不负责事实。

### 记忆层

中等强度：

- 相关才用
- 不相关不强行塞
- 记忆冲突时以当前消息为准
- 没记到就说没记到

### 事实层

来自：

- 当前消息
- 工具结果
- 检索结果
- 已确认配置

不要把三者混成一段大 prompt。

---

## 10. 人工介入点

必须有人工闸的动作：

- 真实发送
- 关注
- 发布
- 删除
- 付款
- 涉及个人信息

人工节点要有：

```text
pending → approved / rejected
```

批准后也不能直接发，仍要过频率和 outbox。

LangGraph 的 `interrupt` / checkpoint 就是把这个“暂停等人”做成状态，而不是靠内存等待。

---

## 11. 持久化执行

Temporal 的核心是 Durable Execution：

- 每次执行有 Event History
- 崩溃后从最后一个事件恢复
- 不丢进度

对本地插件的最小近似：

```text
SQLite:
  runs(id, state, input, output, attempts, updated_at)
  outbox(id, run_id, payload, status, attempts)
  inbox(msg_id, processed_at)
```

不要求一上来接 Temporal，但要有：

- run 表
- outbox 表
- inbox 幂等表
- 失败状态

## 12. 可视化工作流工具怎么选

### Rasa CALM / Flows

适合：

- 对话理解 + 固定业务流程
- 多轮 slot filling
- 企业客服

要点：

- LLM 做理解
- flow 做业务
- slot 不齐就追问

### LangGraph

适合：

- 有状态的 agent / workflow
- 节点 + 条件边
- checkpoint、interrupt、time travel

要点：

- 显式 state
- 节点小
- 人工中断是一等状态

### Temporal

适合：

- 长时间运行
- 跨服务
- 必须 exactly-once 语义的业务

要点：

- workflow 代码可重放
- activity 做副作用
- 重试策略显式

### n8n / Dify

适合：

- 可视化编排
- 快速连接 SaaS
- 非程序员维护

要点：

- 节点要小
- 错误分支要画出来
- 不要把所有逻辑塞进一个 Code 节点

## 13. 工作流的可观测性

每次 run 至少记录：

```text
run_id
trigger
intent
confidence
context_digest
memory_used
policy_decision
reply_hash
send_status
latency
error
```

没有这些，就无法回答：

- 为什么发了这条？
- 为什么没发？
- 为什么重复？
- 为什么答非所问？

---

## 14. 测试与回放

### 必测用例

- 同一消息重复投递
- 插件重载
- 两个轮询器同时启动
- 对方没回，隔 1 小时
- 自己发的消息被当入站
- 发送超时
- 发送成功但回读失败
- 记忆命中 / 未命中
- 低置信问题
- 人工拒绝

### 回放

保存输入事件和策略版本，离线重跑：

```text
同样输入 + 同样策略 → 同样决策
```

LLM 节点允许表达不同，但决策必须可解释。

## 15. 对应到 dsh-webwhale-bili

### 已踩的坑

- 固定兜底句导致刷屏
- 多定时器导致重复
- 内存 seen，重载丢失
- 只按时间冷却，没有 msg_id 幂等
- 会话列表不带 sender，UI 分不清自己/对方
- 生命周期 stop 还发睡前消息
- 前端演示数据参与异常判断

### 目标工作流

```text
DM event
  ↓
inbox 幂等（account + talker + msg_id）
  ↓
conversation lock
  ↓
context: recent 6 + relevant memory + persona
  ↓
intent: self_intro / greeting / memory / faq / task / emotional / risk / unknown
  ↓
policy: owner / mutual / review / confirm / ignore
  ↓
generate: 已知意图才生成；unknown 不发送
  ↓
validate: 相关性、长度、敏感信息、重复
  ↓
outbox
  ↓
rate limit: 1/轮、20min、3/day
  ↓
send
  ↓
record: audit + short memory
  ↓
WAITING
```

### 硬约束

```text
没有新入站 → 不发
同一 msg_id → 只处理一次
同一轮 → 最多 1 条
同一句 → 30 分钟内不重复
未知意图 → 不发
自己发的 → 不入站
插件停止 → 不发
```

## 16. 推荐落地顺序

### P0 安全

- 单例轮询
- inbox 幂等表
- outbox 表
- 去掉固定兜底
- 关闭所有自动发送默认值
- 发送前检查方向

### P1 对话质量

- 意图路由
- 记忆检索
- 自我介绍/FAQ/任务/情绪/风险
- 低置信不回答
- 人工待审

### P2 持久化

- run 表
- 失败状态
- 重启恢复
- 回放

### P3 可视化

- Archify 工作流图
- run 时间线
- 每次发送的证据链

---

## 17. 反模式清单

- 一个巨大的 system prompt 包办所有逻辑
- LLM 决定“要不要真实发送”
- 用内存 Set 做幂等
- 用时间窗口代替消息 ID
- 发送和业务写在同一个函数
- 失败自动无限重试
- 插件 stop 时还发消息
- UI 用演示数据参与真实判断
- 同一个账号启动多个轮询器
- 把“会话对象”当“发送者”
- 没有 run_id，出了问题无法追
- 把“人工确认”做成一个弹窗，而不是状态

## 一句话总结

> 工作流不是“让模型多写几步”，而是把**触发、幂等、状态、路由、人工闸、发送、记录**拆成可验证的节点。  
> 先保证“不该发的一条都不发”，再谈“回得像不像人”。

# 三线工作流设计：AI / 用户 / 审查

> 问题：把 AI 工作流、插件用户工作流、审查工作流拆成三条线，独立又互通，能不能做？会不会更好？

结论：**能做，而且比单一大流程更好。前提是“三条业务线，一个共享事实源”，不能做成三个各自维护状态的系统。**

---

## 1. 三线定义

### A. AI 工作流

负责“理解与表达”：

```text
输入事件
→ 上下文组装
→ 意图识别
→ 记忆检索
→ 候选回复生成
→ 相关性/风格校验
→ 输出候选
```

特点：

- 有概率性
- 可以重试、比较多个候选
- 不能直接写 B站
- 不能决定“是否发送”
- 失败时只影响候选，不影响事实状态

### B. 插件用户工作流

负责“人怎么操作”：

```text
打开工作台
→ 看主页待办
→ 选账号 / 看互动
→ 审阅候选
→ 通过 / 驳回 / 改写
→ 暂停 / 启动
```

特点：

- 确定性
- 由用户动作驱动
- 不生成业务事实
- 所有写操作走 RPC
- 失败时只影响 UI 状态，不直接发送

### C. 审查工作流

负责“什么能出去”：

```text
候选进入审查
→ 身份检查
→ 风险检查
→ 频率检查
→ 重复检查
→ 人工闸
→ 批准 / 拒绝 / 退回
```

特点：

- 独立于 AI 和 UI
- 只做否决或放行
- 不生成文案
- 不直接调用发送
- 所有出站必须经过它

---

## 2. 三者关系

```text
             ┌──────────────┐
外部事件 ───→│ 共享事件/状态 │←─── 用户操作
             └──────┬───────┘
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
   AI 工作流    用户工作流    审查工作流
   （候选）      （指令）      （闸门）
       └────────────┼────────────┘
                    ↓
                 Outbox
                    ↓
                 发送器
                    ↓
                 B站 API
```

关键：

- 三条线不共享内存对象
- 共享**事件表 / 状态表 / outbox**
- 每条线只写自己的表
- 发送器只读审查通过后的 outbox

---

## 3. 共享合同

三条线必须共用同一套 ID：

```text
account_id
conversation_id
event_id / msg_id
run_id
candidate_id
approval_id
outbox_id
```

以及统一状态：

```text
inbox:
  received → classified → candidate_ready / ignored / queued

candidate:
  draft → review_pending → approved / rejected / needs_edit

outbox:
  pending → sending → sent / failed / unknown
```

任何一条线都不能自己发明状态名。

---

## 4. 三条线各自写什么

| 线 | 读 | 写 |
|---|---|---|
| AI | inbox、memory、persona、context | candidate |
| 用户 | inbox、candidate、outbox、health | 用户指令、审批决定、设置 |
| 审查 | candidate、policy、owner、rate、outbox | approval、veto、risk flag |
| 发送器 | approved outbox | send status |

原则：

```text
AI 不写 approval
用户不写 candidate 正文
审查不写 reply
发送器不改 approval
```

---

## 5. 为什么比单一大流程好

### 单一大流程的问题

- 一个 prompt 同时负责理解、写作、审查、发送
- 出错无法定位是哪一段
- 无法单独测试
- 无法人工接管
- 频率/安全规则容易被模型绕过

### 三线的好处

1. **可测试**：AI 只测相关性；审查只测规则；UI 只测状态
2. **可替换**：以后换模型，不动审查和 outbox
3. **可审计**：每个候选都有 run_id 和 approval_id
4. **可回滚**：拒绝候选不影响 inbox
5. **可解释**：为什么没发，能指出是审查哪一条

---

## 6. 风险：三线容易变成三套真相

最常见失败：

```text
AI 线自己记“已回复”
UI 线自己记“已通过”
审查线自己记“已发送”
→ 三边不一致
```

防止方式：

- 只有一张 `candidate` 表
- 只有一张 `outbox` 表
- 状态迁移用条件更新
- 每次迁移写审计
- UI 只读服务端状态，不自己推断
- 发送成功由发送器写，不由 UI 写

---

## 7. 外部硬约束

三条线都受同一组约束：

```text
平台规则
隐私
频率
账号权限
kill switch
人工确认
```

审查线是这些约束的唯一执行者。

AI 线可以“建议”，用户线可以“请求”，但不能绕过审查线。

## 8. 对 dsh-webwhale-bili 的映射

### AI 线

- 意图：self_intro / greeting / memory / faq / task / emotional / risk / unknown
- 记忆：相关才用
- 人格：只负责语气
- 输出：candidate，不直接发

### 用户线

- 主页待办
- 互动列表
- 待审
- 通过 / 驳回 / 改写
- 启动 / 暂停

### 审查线

- owner / mutual / non-owner
- 链接 / 敏感词 / 个人信息
- 频率：1 轮 1 条、20 分钟、3 条/天
- 重复：同句 30 分钟
- 未知：不发
- kill switch：全拒

### 发送器

- 只消费 approved outbox
- 单例
- 失败 unknown 不重试

---

## 9. 是否更好

**是，但只在“共享事实源”这个前提下更好。**

如果做成：

```text
三个独立进程 + 三套数据库
```

会更糟：重复、漂移、不可审计。

推荐：

```text
一个 SQLite / 一个事件表
  ├─ AI worker
  ├─ UI
  ├─ Review worker
  └─ Sender worker
```

这就是“三线作战，一个作战地图”。

## 10. 落地顺序

### 第一步

- inbox 幂等
- candidate 表
- approval 表
- outbox
- sender 单例

### 第二步

- AI 候选生成
- 审查看板
- 用户改写

### 第三步

- 评论链路
- 视频/直播
- 评测与回放

---

## 一句话

> 三线独立是对的：AI 负责“像不像”，用户负责“要不要”，审查负责“能不能”，发送器负责“发不发”。  
> 但三线必须共用同一张状态表和同一个 outbox，否则不是三线作战，是三套真相。
